21) How would you design a scalable URL shortening service like Bitly that handles millions of requests per day?

   A URL shortening service converts a long URL into a short, unique URL.

    Example:
      Original:
       https://www.example.com/products/mobile/samsung-galaxy-s25
       
       Short:
       https://bit.ly/Ab12X

       User submits a long URL.
       Backend generates a unique short code (e.g., Ab12X).
       Stores the mapping in the database.
       When someone visits the short URL, the backend finds the original URL and redirects the user.


22) Explain the trade-offs between monolithic and microservices architectures in terms of deployment, scalability, and maintenance.

    Monolithic Architecture: All features (login, products, orders, payments) are built as one application.
    Microservices Architecture: Each feature is built as a separate independent service.

    Monolithic: Best for small and medium-sized applications.
    Microservices: Best for large applications with millions of users.


      Trade-offs
         Feature	              Monolithic	                 Microservices
         Deployment	    Deploy the entire application	        Deploy each service independently
         Scalability	Scale the whole application	           Scale only the required service
         Maintenance	Easier for small projects	            Easier for large projects but more complex
         Development	Simpler	More complex                      more complex



23) How would you architect a real-time chat application backend to support thousands of concurrent users?     

      A real-time chat backend allows users to send and receive messages instantly without refreshing the page.

      How does it work?
        User logs in.
        Opens a WebSocket connection.
        Sends a message.
        Backend receives the message.
        Stores it in the database.
        Redis broadcasts the message to the correct server.
        Recipient receives the message instantly.

         
         1. Functional Requirements

              Definition:
              Functional requirements describe what the system should do.
              
              Examples
              User can register.
              User can log in.
              User can add products to the cart.
              User can make payments.
              User can send messages.


         2. Non-Functional Requirements

              Definition:
              Non-functional requirements describe how well the system should perform.
              
              Examples
              Response time should be less than 2 seconds.
              Support 10,000 concurrent users.
              99.9% uptime.
              Secure user data.
              Easy to scale.       

             Socket	Pub/Sub
                Client ↔ Server communication	Server ↔ Server communication
                Real-time connection	Message distribution pattern
                Uses WebSocket	Often uses Redis, Kafka, RabbitMQ
                Example: Chat between two users	Sending chat messages to all backend servers          


24) What strategies would you use to ensure high availability in a distributed system?

    High Availability (HA) means the system remains available and operational even if some servers fail.
                
      Strategies
        Load Balancer → Distributes requests across multiple servers.
        Multiple Servers (Replication) → If one server fails, another takes over.
        Database Replication → Maintain copies of the database.
        Caching (Redis) → Reduces database load.
        Auto Scaling → Automatically adds more servers during high traffic.
        Health Checks & Failover → Detects failed servers and redirects traffic.     

    Answer: Use load balancers, multiple application servers, database replication,
     caching, auto scaling, and failover mechanisms so the system continues running even if individual components fail.   


25) Design a rate-limiting system for an API that restricts users to 100 requests per minute. 

     Rate limiting restricts the number of requests a user can make in a given time.

      How does it work?
        Identify the user (by IP address or User ID).
        Store the request count in Redis.
        Allow up to 100 requests per minute.
        If the user exceeds the limit, return 429 Too Many Requests.
        Reset the counter after 1 minute.

       Real-life Example

          Imagine a movie theater.
          
          Each person receives 100 tokens for one minute.
          Every time they enter, one token is used.
          After 100 entries, they must wait until the next minute to get a new set of tokens.
          
          Similarly, the API allows only 100 requests per minute.
